# 文件监听

工作区变了，界面要知道。结构照 Codex 的 `codex-rs/file-watcher` 抄，三层不变：

```
FileWatcher            一个进程一个，管底层 fs.watch
  └ DebouncedWatchReceiver   把一堆事件合成一批
      └ WatchManager         按「谁在听 + 听什么」管生命周期
```

## 三个细节是照抄的，因为都是踩过才知道的

### 一、防抖是固定窗口，不是 trailing

收到第一个事件**开窗**，窗口内的事件全部并进来，到点一次性发出。

trailing debounce（每次事件重置计时器）在持续写入时会**永远不发**——编译产物目录一刷就是
几百次事件，界面就再也不更新了。Codex 用 `deadline = now + interval` 然后 `select!` 到点就发，
同一个意思。

窗口 200ms，两边一致：编辑器保存一次文件通常触发好几个事件，太短前端被刷爆，太长显得迟钝。

### 二、要听的文件还不存在时，听它最近的存在的祖先目录

agent 和编辑器都是「先 watch 再创建」。`fs.watch` 一个不存在的路径直接 `ENOENT`。

做法：向上找第一个存在的**目录**，听那个目录（非递归），再把事件路径映射回原本请求的路径。
没有这一条，「新建文件」永远收不到通知。

而且这带来另一半责任：**听着目录，但只报目标文件**。祖先目录里发生的其他事跟用户无关，
不过滤的话「只看这一个文件」会变成「整个目录一有动静就通知」。

### 三、通知里的路径要排序

同一批事件的到达顺序本来就不稳定。排序之后前端才能稳定比对，测试也才好写。

## 生命周期

`WatchManager` 的三条规矩，都是防真实事故的：

| 规矩 | 不这么做会怎样 |
|---|---|
| 同一个 (客户端, watchId) 不能重复注册 | 覆盖就漏了前一个 `fs.watch` 的引用，进程里悄悄多一个句柄 |
| `unwatch` 先把攒的一批发出去再关 | 已经发生的变化因为用户点了「别听了」而消失 |
| 连接断开清掉该客户端全部 watch | 标签页反复开关，句柄一路泄漏 |

`watchId` 的作用域是客户端，不同标签页用同一个 id 互不影响。

## 接到界面上

`/api/stream`（SSE）连上后自动监听当前工作区（递归）。变化推 `fs/changed`：

```json
{ "paths": ["/home/u/proj/src/a.ts", "/home/u/proj/src/b.ts"] }
```

前端显示一条浮在底部的胶囊：`↻ 2 files changed outside this session — click to refresh`。

三个刻意的选择：

- **不往过程流里塞**。那不是 agent 做的一步，塞进去会打乱「他做了什么」的顺序感。
- **不自动刷新**。正在读的内容被人从外部改了、界面自动重载，会让人以为是自己手滑。
  让用户决定什么时候看。
- **挂到 body，用 fixed 定位**。第一版用的是 `sticky` 且挂在过程流容器里，结果它被当成
  flex item 拉满整块，把内容挤成一条窄缝——截图一看就知道，不看截图看不出来。

## 验证

```bash
node --test tests/watch.test.mjs
```

13 个测试。前五个是纯防抖（成批、去重、排序、**持续写入仍会 flush**、关闭后不再发），
中间四个用真实文件系统（目录、尚不存在的文件、祖先目录的兄弟文件不被报、递归），
最后四个是生命周期（重复 id、unwatch 后静默、连接断开释放、取消没听过的东西是 no-op）。

界面在浏览器里验过：连上 SSE → 外部写文件 → 胶囊出现且计数正确。
