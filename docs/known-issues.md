# Known issues

## KI-1 — musl SEA segfaults on aarch64 (blocks static Linux builds)

**Status:** open, not blocking P0/P1. Linux ships glibc instead.

**Symptom.** Building a Node SEA inside `alpine:3.22` with its bundled
`nodejs` v22.23.4 (musl), then injecting the blob into that same binary, produces
a binary that segfaults at startup — before any application code runs.

**What was tried (2026-11-12, aarch64):**

| Method | Result |
|---|---|
| `postject --sentinel-fuse NODE_SEA_FUSE_...` | `Segmentation fault (core dumped)`; `strings` still contains 1 un-replaced `NODE_SEA_FUSE` marker |
| `objcopy --add-section NODE_SEA_BLOB=...` | no crash, but `--version` prints `v22.23.4` — the blob is never loaded, because the section is emitted outside any `PT_LOAD` segment |

The blob is generated by the *same* musl binary used as the base, so this is not
a version mismatch.

**Workarounds in use now**

- Linux release artifacts target `*-unknown-linux-gnu` (glibc >= 2.28).
- Alpine / container users: npm JS mode (`@unit-harness/cli` without the SEA
  binary) or the Docker image.
- README must not claim Alpine support while this is open.

**Next attempts**

1. `unofficial-builds.nodejs.org` static musl node as the SEA base (official
   `nodejs` in Alpine is dynamically linked against `ld-musl`, which may be the
   root cause).
2. Reproduce on x86_64 musl to see whether this is aarch64-specific.
3. Newer `postject`; check its ELF handling for non-default page sizes
   (ARM64 images often use 64 KiB pages).

Narrowing 1 vs 2 first is the cheapest step: if x86_64 musl works, the problem is
aarch64-specific ELF handling, not musl per se.

## KI-2 — Windows has no kernel isolation yet

**Status:** open. Windows reports `path-guard` and fails closed.

**Symptom.** On `win32`, `uh doctor` reports `isolation none … [available path-guard]`
and `exec` refuses to run without `--allow-unconfined`.

**Why.** Both real options need a native helper compiled with MSVC:

- **Restricted token** (`CreateRestrictedToken` + `CreateProcessAsUser`): drops
  privileges, but does not by itself confine file access.
- **Job Object**: bounds memory/CPU/process count, but does not restrict paths.

A meaningful Windows sandbox needs both, plus path ACLs for the workspace — that is
a native module, and it must still be verified on a real runner before we claim it.

**What CI enforces today.** The `windows-latest` job asserts the *honest* state:
doctor reports `path-guard` and `uh tool hello` is refused. This prevents a future
change from silently enabling unconfined execution on Windows.

**Next step.** Write `native/token-run` (C, MSVC), have CI compile and run it, and
only then flip `enforced` to `win-restricted-token`.
