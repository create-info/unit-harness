# Spike results (2026-11-12)

Environment: Linux 6.17.0-1008-nvidia, aarch64, Node v22.22.3, Docker 27.x.
All numbers below are from actual runs, not estimates.

## S1 — SEA + dynamic ESM plugin loading

**Question:** can a Node SEA single-file binary `import()` an ESM plugin from a
user directory (`~/.uh/plugins/<name>/index.js`)?

**Result: PASS.**

| Attempt | Output | Verdict |
|---|---|---|
| `esbuild --format=esm` → SEA | `SyntaxError: Cannot use import statement outside a module` at `embedderRunCjs` | FAIL — Node 22 SEA entry must be CJS |
| `esbuild --format=cjs` + `new Function('s','return import(s)')` | `[plugin:hello] apply() called` / `SEA_DYNAMIC_IMPORT_OK` | PASS |

Binary size: **117 MB** (node 22.22.3 arm64 + bundled host).

Two implementation constraints found:

1. The SEA entry point **must be CommonJS**. Node 22 does not support an ESM
   `main` in SEA (`internal/main/embedding:60 embedderRunCjs`).
2. Wrapping the dynamic import as `new Function('s','return import(s)')` is
   required so the bundler cannot rewrite it into a `require` chain.

## S1b — Cordis inside SEA

**Question:** does `@deepseek-ai/cordis@4.0.1` (npm, MIT) survive esbuild bundling
into a CJS SEA, and can an external plugin be mounted on it?

**Result: PASS.**

```
[host] Context created: true
[host] ctx.plugin() accepted: @example/hello
[plugin:hello] apply() called
[host] ctx.hello = object
[host] RESULT: CORDIS_SEA_OK
```

Conclusions:

- A plugin can be `{ name, apiVersion: 1, apply(ctx) }` with **zero runtime
  dependency** on cordis — no `node_modules` needed next to the plugin.
- `ctx.provide()` from inside a plugin lands on the Cordis context and is visible
  as `ctx.<name>`.
- A plugin file without `"type": "module"` in the nearest `package.json` triggers
  `MODULE_TYPELESS_PACKAGE_JSON` plus a re-parse penalty → plugin authors must
  ship `package.json` with `"type": "module"`.

## S2 — musl SEA (aarch64)

**Question:** can we ship a static musl build (Alpine, glibc-free)?

**Result: FAIL — segfault.**

Tested inside `alpine:3.22` with its own `nodejs` v22.23.4 (musl):

```
== musl node: v22.23.4 | libc: musl
== 1. sea blob                              -> Wrote single executable preparation blob
== 3. inject into musl node base (postject) -> Injection done!
== 4. size: 49.5M
== 5. RUN                                   -> Segmentation fault (core dumped)
```

The blob is generated by the *same* musl binary that is then used as the base, so
this is not a version mismatch. It crashes before any of our code runs.

### S2 follow-up: postject vs objcopy (same session)

| Path | `readelf` | `--version` | Verdict |
|---|---|---|---|
| `postject` inject | section present | segfault (139), `strings` still shows **1** `NODE_SEA_FUSE` -> fuse not replaced correctly | unusable |
| `objcopy --add-section` | `NODE_SEA_BLOB PROGBITS` present, but linker warns `allocated section not in segment` | `v22.23.4` (bare node) -> **blob never loaded** | unusable |

`objcopy` avoids the crash only because the section is not mapped into a
`PT_LOAD` segment, so the runtime never finds the blob.

**Conclusion: musl SEA on aarch64 is not usable today.** Linux ships glibc
(>= 2.28); Alpine users get the npm JS mode or the Docker image.

Implication for `docs/release.md`:

- Linux artifacts should be **glibc-based** (require glibc >= 2.28) until musl SEA
  is solved; Alpine users get the npm JS mode or the Docker image instead.
- Re-test with: (a) unofficial-builds musl node (static), (b) `objcopy
  --add-section` instead of postject, (c) a newer postject release.
- Do not claim musl support in the README until one of those passes.
